# HealthMate architecture and conventions

This document is the source of truth for how the repository is organized and how code gets written. It applies to humans and coding agents equally. If code and this document disagree, one of them is wrong and gets fixed in the same PR.

## Principles

1. **The domain is the only writer.** Every state change goes through a use case in `core`. Clients, the agent and channels never write directly.
2. **The agent proposes, people confirm.** The agent can draft, ask and create pending proposals. It never persists a record.
3. **History is never lost.** Records are corrected with new versions, never overwritten or deleted.
4. **Time is never invented.** Imprecise time is stored as imprecise. Missing time is asked for.
5. **Validate at the edges, trust the inside.** Untrusted input is parsed once at a boundary. Code inside `core` assumes valid data.
6. **Small, boring, explicit.** Functions and plain objects over classes and frameworks. Add an abstraction the second time you need it, not the first.

Root holds only workspace configuration, `supabase/` (local stack config and migrations), `scripts/` (local stack orchestration), `.env.example` and `CLAUDE.md`. Technical docs, ADRs and the data schema live in `docs/technical/`. Scripts stay thin shell orchestration, and any logic that needs tests belongs in a package. No `infra/` until v1.0. No shared utilities package. If two packages need the same helper, one of them owns it and exports it.

Inside any package, a folder gets subfolders only when it passes roughly eight files.

## Packages

| Package | Responsibility |
|---|---|
| `core` | Domain rules and use cases. Zero runtime dependencies. |
| `contracts` | Everything that crosses a process boundary: HTTP payloads, channel events, client views and a small typed API client. |
| `db` | Postgres access, the Drizzle schema that generates `supabase/migrations`, synthetic seeds, and implementations of `core` repository ports. |
| `agent` | Conversation loop, tools, prompts, policy, budgets and citation validation. Defines the ports for model and transcription. |
| `providers` | Concrete implementations of `agent` ports for real model and transcription services. |
| `evals` | Datasets, runner, scorers and committed run summaries. Nothing depends on it. |
| `apps/api` | Composition root. The only place that builds concrete implementations and wires them together. Maps between `core` and `contracts`. |
| `apps/telegram`, `apps/mobile` | Thin channel adapters that talk to `api` through the client in `contracts`. |

## `core` layers

| Layer | Contains | May import | Never |
|---|---|---|---|
| `domain` | Entities, value types, invariants, pure rules | Other `domain` code | `async`, I/O, `ports`, `application` |
| `ports` | Interfaces for everything outside the domain | `domain` (types only) | Implementations of any kind |
| `application` | Use cases that orchestrate domain rules through ports | `domain`, `ports` | Concrete implementations, `testing` |
| `testing` | In-memory implementations of every port | `domain`, `ports` | Being imported by `domain` or `application` |

- `domain` answers "what is valid". It returns decisions and touches nothing.
- `ports` answers "what does the domain need from the outside world". Repositories, clock, id generation and transactions are interfaces here.
- `application` answers "what can someone do". A use case loads through ports, asks `domain` for a decision, and writes through ports.
- `core` has two entry points. `@healthmate/core` exports use cases, domain types and port interfaces, and `@healthmate/core/testing` exports the in-memory ports.

Modules (entries, records, proposals, timeline, audit) repeat inside each layer. A module that owns versioning knows nothing about entry kinds. Proposals can depend on entries and records. Entries and records never depend on proposals.

### Where types live

- Domain types live in `domain`, with the module they belong to.
- Interfaces live in `ports`, one per file.
- A use case's dependencies, input and error union live in the same file as the use case.

There is no `types/` or `interfaces/` folder. Grouping by kind of TypeScript construct separates things that change together.

| Package | May import |
|---|---|
| `core` | nothing |
| `contracts` | `zod` |
| `db` | `core`, Postgres libraries |
| `agent` | `core`, `contracts`, `zod` |
| `providers` | `agent` (types only), provider SDKs |

| `apps/api` | everything except `evals` |
| `apps/telegram`, `apps/mobile` | `contracts` |

Enforced in CI with `eslint-plugin-boundaries`, including the layer rules inside `core`. Package `exports` maps make deep imports from other packages fail to resolve.

## Types, schemas and stored shapes

Three kinds of shapes exist. They change for different reasons, so they live in different places.

| Shape | Purpose | Location | Naming |
|---|---|---|---|
| Domain type | What something is and its rules | `core/domain` | `Symptom`, `Proposal` |
| Wire schema | What crosses a boundary | `contracts`, or the agent tool that receives it | `proposalViewSchema`, `ProposalView` |
| Stored shape | How it's persisted | `db` | `SymptomRow`, `symptomPayloadV1` |

- `core` never imports `zod` and never uses `z.infer`.
- In `contracts` the schema is the source of truth, so `z.infer` is correct there.
- Values with rules are created by a function that validates them and returns a `Result`. Code that receives one can trust it.
- Each boundary has exactly one mapper. The API maps HTTP, the tool handler maps agent arguments, and the repository maps storage.
- Some duplication between the three shapes is expected and accepted.

## Writing use cases

A use case is an async function that takes its dependencies first and its input second, and returns a `Result`. The decision belongs to a pure function in `domain`; the use case only loads, asks and writes.

```ts
export type ConfirmProposalDeps = { uow: UnitOfWork; clock: Clock }

export type ConfirmProposalError =
  | "not_found"
  | "already_confirmed"
  | "expired"
  | "stale"

export async function confirmProposal(
  deps: ConfirmProposalDeps,
  input: { proposalId: string; actorId: string },
): Promise<Result<{ recordId: string }, ConfirmProposalError>>
```

- Expected failures are values in the error union. Throwing is reserved for bugs and infrastructure failures.
- Anything that writes more than one thing runs inside a single unit of work.
- Time comes from `Clock`, ids from `IdGenerator`. Never call `Date.now()` or generate ids inline in `core`.
- Error names are snake_case string literals so they serialize cleanly to the agent and the API.

## Agent rules

- Tool arguments are parsed with the tool's schema. Invalid arguments are returned to the model as errors, never repaired.
- Required fields come from `core`. The agent asks for what `core` says is missing, one question at a time, and never asks about optional fields.
- Vague magnitudes ("pretty bad") are asked about, never converted to numbers.
- An ambiguous reference to an existing record produces a question, never a guess.
- Every cited id must come from a tool result in the same turn, verified in code.
- Every turn has a step limit, a token limit and a timeout. Hitting one ends the turn with a visible failure.
- Stored content reaches the model only inside tool results, clearly delimited. Instructions inside stored content are never followed.
- Red-flag responses use fixed, reviewed copy, never generated text.
- Prompts are versioned files. Changing a prompt means a new version, never an edit.
- Every proposal records the model, prompt version and source transcript.

## Data rules

- v0.1 uses synthetic data only.
- There are two environments. The local Supabase stack holds demo data, and a separate hosted Supabase project holds personal data. Tests, seeds and evals refuse to run unless every connection points at a loopback host.
- App tables live in `public`, which PostgREST does not expose, and every table has row level security enabled with no policies. Only `apps/api` reads and writes app data, as the table owner, through `core`.
- The Supabase secret key is server-only. Channels and clients never receive it.
- Logs never contain record content, transcripts or prompts. Log ids, kinds, durations and error names.
- Audio is discarded after transcription. The transcript is kept as the source.

## Testing

| Layer | How |
|---|---|
| `core/domain` | Pure unit tests, no fakes |
| `core/application` | Unit tests against `core/testing` |
| `db` | Integration tests against the local Supabase Postgres, each in a rolled-back transaction |
| `agent` | Loop and tools with a scripted model client replaying recorded responses |
| `apps/api` | Route tests with fakes wired in |
| Model behavior | Live evals against the real model, run separately |

The regular test suite never calls a real model or the network. Eval summaries are committed.

## Working with coding agents

`CLAUDE.md` points to this document and contains nothing that contradicts it.

Agents do not do these things unless the task asks for them explicitly.

- Create or edit migrations
- Edit `contracts`
- Edit agent policy, prompts or eval datasets
- Add dependencies
- Change the dependency rules or this document

Every task names the package it touches, the use case or tool involved, and the tests that must pass. One task, one PR.

## Definition of done for a PR

- Typecheck, lint and boundaries pass
- New behavior has tests at the right layer
- No real data, no content in logs
- If a decision was made, an ADR exists or is updated
- If agent behavior changed, evals were run and the summary is committed

## Kickstart checklist

1. Initialize the workspace, Turborepo, TypeScript, ESLint and Vitest with empty packages and their `exports` maps.
2. Add boundary rules and confirm a forbidden import fails CI.
3. Local Supabase stack through the CLI, with scripts to start it, write `.env.local`, migrate and seed.
4. Write ADR-001 (stack) and a first draft of the threat model.
5. Define the first table in the Drizzle schema and commit the generated migration.
6. In `core`, write the domain with pure tests, then the ports, then the use cases tested against `core/testing`.
7. In `db`, write the repositories, the unit of work and the integration tests.
8. In `agent`, write the loop, the budgets and the tools against a scripted model client.
9. Write the first 25 eval cases before connecting a real model.
10. In `providers`, connect the real model and the transcription service.
11. In `api`, add the conversation, proposal and timeline routes.
12. `telegram` as the first channel, then the timeline view in `mobile`.
