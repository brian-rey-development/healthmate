# v1.0 · Production

Not started.

## Goal

Run HealthMate in the cloud with the same guarantees it has locally.

## Scope

**In.** Infrastructure as code, a real KMS behind the existing key provider port, and managed Postgres and object storage. Observability and alerts without content, scheduled backups and an incident runbook.

**Out.** New product features. Everything user-facing is already shipped by v0.8.

## Entry criteria

- [ ] v0.8 shipped
- [ ] The `infra/` folder is allowed in `docs/technical/architecture.md` from this release

## Decisions

- [ ] Cloud provider and which services to manage yourself
- [ ] SLOs for a single-user product
- [ ] Backup schedule, retention and restore drill cadence

## Work plan

- [ ] `infra` · Infrastructure as code for every environment, created from scratch in a clean account.
- [ ] `apps/api` · Real KMS adapter behind the key provider port, with no change in `core`.
- [ ] `apps/api` · Traces, metrics and alerts, checked by the same no-content test used locally.
- [ ] Scheduled encrypted backups and a timed restore drill in the cloud.
- [ ] Incident runbook and one simulated incident with a written postmortem.
- [ ] Case study linking every ADR, eval summary and release note.

## Acceptance criteria

- [ ] A fresh environment is created entirely from code
- [ ] Switching to real KMS required no changes in `core`
- [ ] A full restore in the cloud is timed and documented
- [ ] Observability contains no record content, verified by the same automated test as locally
- [ ] A simulated incident has a written postmortem
- [ ] A final case study links every ADR, eval summary and release note, and reports how much domain code changed to reach production
- [ ] Release checklist complete

## Risks

| Risk | Mitigation |
|---|---|
| Cloud configuration drifts from code | Every change goes through the infrastructure code, and a fresh environment is rebuilt as an acceptance check |
| Observability tooling captures request bodies by default | The no-content test runs against the real telemetry pipeline |

## Demo script

1. Create a fresh environment from code.
2. Log a symptom through Telegram against the cloud deployment.
3. Show the trace for that request with ids and durations only.
4. Run the restore drill and show the timeline intact.
