# v0.1 · Capture

In progress since 2026-10-22.

## Goal

Prove that logging through the agent takes less time than the form, with the same accuracy. The demo measures both. The person confirms every record before it is saved.

## Scope

**In.** Notes and symptoms captured by text or voice through Telegram and by form on the web. The agent drafts proposals and asks for missing required fields one at a time. The person confirms, edits or discards. Records are corrected with new versions. A timeline on the web shows everything. The agent answers read-only questions about the timeline with citations.

**Out.** Auth, encryption, files, labs, real data. All data in this release is synthetic and lives in the local stack.

## Entry criteria

- [x] Workspace, Turborepo, TypeScript, ESLint and Vitest with boundary rules (ADR-001)
- [x] Local Supabase stack with migrations and a seed (ADR-002, ADR-003)
- [ ] Repository on GitHub with CI running on every push

## Decisions

Each decision gets an ADR before the code that depends on it is written.

- [x] Record identity, corrections, time and precision. One `entries` table with the current data and an `entry_history` table filled by a trigger (`docs/technical/data-schema.dbml`).
- [ ] Required fields per entry kind. Decides what the agent asks and what the form requires. Recorded in the zod schemas and `docs/technical/data-schema.dbml`.
- [x] How to name symptoms. A `subjects` table with seed rows for all users and private rows for each person (`docs/technical/data-schema.dbml`).
- [ ] Timeline ordering, and whether corrections show openly or one step away. ADR-004.
- [ ] Transcription hosted or local, and which provider. Must meet the zero data retention rule before v0.2. ADR-005.
- [ ] Model and agent loop, own loop or SDK, and how budgets are enforced. ADR-006.
- [x] Stack (ADR-001, amended by ADR-002 for Drizzle and ADR-003 for Supabase)

## Acceptance criteria

**Capture**

- [ ] "Headache since 3pm, 6 out of 10" by text produces a symptom proposal with onset today at 15:00 and severity 6, with no question asked
- [ ] The same message by voice produces the same proposal, with the raw transcript visible
- [ ] Notes are captured as written, without rephrasing

**Clarification**

- [ ] "Headache, pretty bad" produces exactly one question, about severity, and no proposal until answered
- [ ] Missing optional fields never produce a question
- [ ] "A while ago" produces a question about time
- [ ] "Last March" is stored with month precision, not as a specific day

**Proposals**

- [ ] No record exists before confirmation
- [ ] Confirming the same proposal twice creates exactly one record
- [ ] An expired proposal cannot be confirmed
- [ ] Editing a proposal before confirming persists the edited version
- [ ] A discarded proposal leaves no record

**Corrections**

- [ ] Correcting from the UI creates a new version, and the original is still viewable
- [ ] "Yesterday's headache was a 7" with one matching record produces a correction proposal
- [ ] The same message with two matching records produces a question, not a guess
- [ ] A correction drafted on an outdated version is rejected and redrafted

**Timeline**

- [ ] Shows notes and symptoms together, filterable by kind
- [ ] Corrected entries and backfilled entries are visibly marked
- [ ] Renders the synthetic seed correctly

**Reads**

- [ ] Questions about the timeline are answered with citations to real records
- [ ] An answer citing a record not returned by a tool in that turn is rejected (tested with a scripted model)
- [ ] Questions with no matching data get an honest "no records" answer

**Safety and personality**

- [ ] Requests for diagnosis or advice get the standard refusal
- [ ] Red-flag entries show the fixed message, and the entry can still be logged
- [ ] Personality eval passes with no emojis, no exclamation marks, no wellness language and one question at a time

**Robustness**

- [ ] A turn that exceeds its step, token or time budget fails visibly
- [ ] Invalid tool arguments are returned to the model and never repaired
- [ ] Instructions inside a stored note are not followed (eval case)
- [ ] The app is fully usable with the agent disabled

**Data**

- [ ] Tests, seeds and evals refuse to run against the personal environment (db tests and seeds done, evals pending)
- [ ] An automated test confirms logs contain no record content, transcripts or prompts
- [ ] Audio is deleted after transcription

**Quality**

- [ ] All v0.1 eval suites pass their thresholds
- [ ] Release checklist complete

## Evals

Capture, Clarify, Corrections, Reads, Safety and Personality are introduced here. At least 25 cases exist before a real model is connected. The first committed summary is the baseline, and later releases must not regress against it.

## Risks

| Risk | Mitigation |
|---|---|
| The record model is wrong and every later release inherits it | `docs/technical/data-schema.dbml` is reviewed before any `core` code, and v0.3 to v0.6 kinds are sketched against it |
| The agent feels slower than a form | Median time from message to confirmed record is measured in the demo and compared with the form |
| Transcription quality hides behind good text evals | Voice cases in the Capture suite use real recordings of synthetic scripts |
| Scope creep into auth or encryption | Both are out of scope until v0.2, and the local stack holds only synthetic data |

## Demo script

1. Send "Headache since 3pm, 6 out of 10" in Telegram and confirm.
2. Send a voice note with the same content and show the transcript on the proposal.
3. Send "Headache, pretty bad", answer the single severity question, and confirm.
4. Send "Yesterday's headache was a 7" and confirm the correction, then open both versions on the web timeline.
5. Ask "How many headaches this month?" and open each cited record.
6. Ask "Is this a migraine?" and show the refusal.
7. Disable the agent and log a symptom with the form.
