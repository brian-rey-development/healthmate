# v0.2 · Lock it down

Not started.

## Goal

Make HealthMate safe enough to hold real health data.

## Scope

**In.** Passkey login and envelope encryption for payloads and transcripts. Per-user row level security and an audit log that the person can read. Encrypted backups with a tested restore, and providers that meet the zero data retention rule. The hosted personal Supabase project is created in this release.

**Out.** New record kinds, files and cloud deployment of the app itself. Real data enters only after every acceptance box is checked.

## Entry criteria

- [ ] v0.1 shipped
- [ ] Red-flag list and copy sent for review by someone with medical background

## Decisions

- [ ] Which data is sensitive, only the payload, or also timestamps and record kinds
- [ ] Key granularity and rotation
- [ ] What counts as an auditable event
- [ ] Account recovery if a device is lost
- [ ] Telegram's status with real data
- [ ] Model and transcription providers with zero data retention
- [ ] Whether Supabase Auth covers passkeys or a separate WebAuthn layer is needed

## Work plan

- [ ] `core/ports` and `core/domain` · Key provider port and an encrypted payload type, so `core` never sees key material. Unit tests.
- [ ] `database` · Local key provider, envelope encryption of payloads and transcripts in the repositories, migration for wrapped data keys. Integration test that reads raw rows and finds no plaintext.
- [ ] `database` · Per-user RLS policies keyed on the Supabase user id. Integration test that a second user's direct query returns nothing.
- [ ] `core/application` · Audit events written in the same unit of work as every decrypted read, proposal, confirmation and export. Unit tests.
- [ ] `apps/api` · Passkey authentication through the chosen option, session handling and the access log endpoint. Route tests.
- [ ] `apps/mobile` · Login and access log view.
- [ ] `apps/telegram` · Account linking, or synthetic-only mode, depending on the Telegram decision.
- [ ] `scripts` · Encrypted backup and restore, with a timed restore into a fresh database.
- [ ] Hosted personal Supabase project created, migrations applied with `db push`, secrets stored outside the repository.
- [ ] Threat model updated for every data flow.

## Acceptance criteria

- [ ] Payloads and transcripts are unreadable in the database without the key
- [ ] An automated test fails if sensitive plaintext appears in the database, logs or traces
- [ ] A user cannot read another user's records, even with a direct query that bypasses the app
- [ ] Every read of decrypted content, proposal and confirmation appears in the access log
- [ ] The person can see their own access log, including agent reads
- [ ] A key rotation has been performed and documented, with all data still readable
- [ ] A full restore into a fresh database has been timed and documented
- [ ] Losing a device has a documented recovery path that was tested
- [ ] Red-flag list and copy reviewed by someone with medical background
- [ ] Release checklist complete

## Risks

| Risk | Mitigation |
|---|---|
| Encryption breaks timeline queries that filter on payload fields | Decide what stays queryable in plaintext before writing the migration |
| Lost passkey locks the only user out | Recovery path is designed and tested before real data arrives |
| Real data reaches a provider that retains it | Provider decision is an entry condition for real data |

## Demo script

1. Log in with a passkey.
2. Log a symptom, then show the raw row in the database is unreadable.
3. Open the access log and find the agent read from a question.
4. Restore a backup into a fresh database and show the timeline intact.
